How the whole
app connects

Six plates, drawn from the source rather than from memory: what talks to what across the network, how a URL becomes a guarded page, where every piece of state actually lives, and the three flows — a task, an hour, a family’s access code — that carry the product. One app ships two products from one bundle: a staff operations tool behind a login, and a public parent portal with no account at all.

Plate 1 · System

One bundle, one key,
two audiences

There is no backend of our own. Vercel serves a static React build; every request after that goes from the browser straight to Supabase using the anon key that ships inside the public bundle. That single fact sets the security model: what a signed-out visitor may see is decided entirely by row-level security in Postgres, not by anything the client does.

Plate 2 · Routing & access

The fork at the
front door

/ is a chooser, not a login — and it is shown on every visit with no remembered side. Staff go left into a session-guarded app where a second guard splits admin from team. Families go right into pages that never authenticate at all; their gate is a bcrypt code checked by a database function, remembered per device.

Plate 3 · Provider tree

Fifteen layers,
one straight line

Every provider in App.tsx wraps the next — there are no siblings, so the tree is really a chain. That matters for two reasons: anything above Router mounts on every route including the public portal, and a context that fetches on mount without checking for a session will fire requests on a family’s device. Only PortalProvider is scoped to its routes.

Plate 4 · Wiring

Every context,
and what backs it

Pages hold almost no data of their own — they read a context, and each context owns exactly one slice of storage. Trace any value on screen back through this plate and you land on either a Postgres table with an RLS predicate, or a key in the browser that no one else can see.

Plate 5 · Lifecycles

Three flows that
carry the product

Everything else is scaffolding around these: a task moving from a library entry to a completed checklist, an hour moving from a phone in the field to frozen payroll, and a family moving from a link to a document. Each one crosses a boundary where the database, not the client, is the authority.

Plate 6 · Freshness & offline

Four ways state
gets current

The app is used on phones, in buildings, by people who lock the screen mid-task. So no single refresh path is trusted: a fetch on mount, a live socket, a re-fetch when the tab comes back, and a queue for writes made with no connection at all.

Notes · Sharp edges

What the diagrams
won’t warn you about

Seven things that are true of this codebase today and are easy to get wrong when changing it.

Calendar events never leave the device

EventContext reads and writes three localStorage keys and has no Supabase call at all — no events table exists. Two people looking at the same calendar see different events, and clearing site data deletes them. Tasks on that same calendar are shared, which makes the split easy to miss.

src/contexts/EventContext.tsx

Staff contexts mount on portal routes

DataProvider sits above Router, so every staff context mounts for a signed-out family too. WorkHoursContext short-circuits its fetch and its channel when there is no session, which is what got a portal load down to three requests. A new context that fetches unguarded puts those requests back.

src/App.tsx · src/contexts/PortalContext.tsx (header)

Pay data is gated in the database, not the UI

employee_pay_rates and work_hours_pay are RLS-gated on is_admin(), so for a team member the context arrays are simply empty. There is no client-side filter to preserve — and equally, none to rely on if you ever loosen those policies.

src/contexts/WorkHoursContext.tsx · migration v7

The portal gate is soft, on purpose

Portal content is readable by the anon role because a portal with no login has to be. The bcrypt code stops casual browsing; it cannot stop anyone holding the anon key, which ships in the public bundle. Nothing private belongs in portal_* content.

migration v9 header · src/pages/portal/ProgramGate.tsx

Activity logs are written twice

logActivity() inserts into activity_logs and mirrors to localStorage, and the log page reads both. The mirror is per-device and uncapped, so an admin’s history looks different on their laptop than on their phone.

src/utils/activityLogger.ts · src/contexts/ActivityLogContext.tsx

Jobs are wired but unreachable

JobProvider mounts, subscribes to a realtime channel and queries the jobs table on every staff load, but the only consumer of useJob() is JobForm, which no page imports. work_schedule_templates has no client code at all. Both are cost with no surface.

src/contexts/JobContext.tsx · src/components/JobForm.tsx

Offline covers four stores, not the app

The IndexedDB queue replays sops, job_tasks, task_templates and users. Hours, calendar events, portal content and logs are not queued — on those screens an offline write fails rather than waiting for reconnection.

src/lib/indexedDB.ts · src/hooks/useOfflineSync.ts

Theme tokens are CSS variables, not hex

theme.colors.bg.* resolves to var(--c-bg-primary, …). Concatenating an alpha suffix onto one, or passing one as an SVG presentation attribute, silently produces an invalid value — the element renders with no colour rather than throwing.
